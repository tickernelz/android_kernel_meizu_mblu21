# Hardware results: 2026-11-02 session on the mBlu 21 (M416H)

Everything below was measured on the real phone (`416HF61E8DFT009433`, board `ums9230_6h10`, kernel `5.15.149-android13-8-00008-gbe074b05e5af-ab12096863`), not inferred from the images. Where an item is **not** proven, it says so.

## What the bootloader enforces

The phone was unlocked with the CVE-2022-38694 BootROM method (`ums9230_universal_unlock_UFS`), which sets the unlock flag in `miscdata` and does **not** run the usual userdata wipe: after unlocking, `/data` still held 2.9 GB, 255 packages, and FBE was active. `ro.boot.flash.locked=0`, `verifiedbootstate=orange`.

| Written | Result |
|---|---|
| stock `vbmeta_a` (flags 0, Meizu signature) | boots |
| `vbmeta` flags 3, algorithm NONE (the `fastboot --disable-verification` form) | stuck at the logo |
| `vbmeta` flags 3, **signed** RSA-4096 with the AOSP test key, no chain descriptors | stuck at the logo |
| stock `vbmeta_a` + foreign `vendor_boot_a` (SHRP) | stuck at the logo |
| stock `vbmeta_a` + stock `boot_a`/`vendor_boot_a`/`dtbo_a` + **modified `init_boot_a`** | **boots** |

So the top-level `vbmeta` must be Meizu-signed even with the bootloader unlocked, and `vendor_boot` is verified against the key in its chain descriptor (`4fce36c7…`). `init_boot` is a chain partition in `vbmeta_a` (`f1553ffc…`) but verification of it is **not** enforced in practice — a one-byte header change (`0x20`: `00`→`ff`) booted, which is what made the LKM root path possible.

Unverified, and the reason the kernel path is still labelled untested here: no image with a foreign signature was ever written to `boot_a` while everything else stayed stock. Flashing `boot-<variant>.img` is the one experiment left for that path, and a failed boot costs a download-mode recovery window, so it was not run unattended.

## Write path

`fastboot flash` and `fastboot boot` are read-only on this unit: they answer `Sending … OKAY` and then fail at `Writing` (`Status read failed (No such device)`) or never start. Everything that was written went through `spd_dump` in Unisoc download mode (USB `1782:4d00`), entering it with **Volume Up + plug in** (Volume Down gave only the charging screen). Each `spd_dump` session drops the link on reset, so every write needs a fresh hold-and-plug window.

In both cases `getenforce` stayed **Enforcing**, the kernel stayed the stock `5.15.149` build, and `boot`, `vendor_boot`, `dtbo`, `vbmeta` were left at their stock Meizu content. Live partition hashes at the end of the session: `boot_a` `3a78e139…` (= stock), `init_boot_a` `cd060b9e…` (patched), `vendor_boot_a` `c053086c…` (= stock), `vbmeta_a` `83789a72…` (= stock), `dtbo_a` `71e5cae7…` (= stock).

### How the SukiSU-Ultra image was produced

SukiSU-Ultra v4.3.0 publishes `ksud` for Android only, so the patch ran **on the phone**, not on a build host:

```sh
/data/adb/ksud boot-patch -b /data/local/tmp/init_boot.stock.img \
  -m lkm-aarch64-android13-5.15_kernelsu.ko \
  --kmi android13-5.15 --partition init_boot
```

The output was pulled and written to `init_boot_a` through download mode. The same command with KernelSU-Next's `ksud` and LKM reproduces the other image, but that one is also built in CI (`scripts/patch_init_boot.sh`) because KernelSU-Next ships a host-side `ksud`.

## SUSFS (root hiding) on the LKM path

`susfs_guard_lkm.ko` `024aa0de96b9e2d45c7f9a086189d72f95d51028fec6621b48e5f548cd39dc26` (v2.3.0-gki, 601 624 B) is the KernelSU-Next SUSFS module. It attaches to **SukiSU-Ultra** as well, because it resolves the root driver's symbols by name at load time (`ksu_uid_should_umount`, `ksu_patch_text`, `add_try_umount` are all present in SukiSU-Ultra 4.3.0's `kernelsu.ko`) instead of linking against a fixed CRC.

| Check | Result |
|---|---|
| `ksud susfs implementation` / `version` / `variant` / `status` | `lkm` / `v2.3.0` / `GKI` / `true` |
| Manager home screen | `SuSFS Version v2.3.0 (Tracepoint Syscall Redirect)` |
| Supercall transport | kprobe on the `reboot` syscall — dmesg `susfs supercall: armed (reboot ABI, version v2.3.0)` |
| `/proc/susfs_*` | `path`, `kstat`, `opath`, `open_redirect`, `enable_log`, `avc_spoof`, `hide_modules`, `hide_mounts` |
| `ksud susfs set-uname` | `uname -r`/`uname -v` from a non-root shell showed the spoofed strings, then the stock strings were restored |
| `lsmod` | empty by design; the module removes itself from `/proc/modules` for every caller, use `/sys/module/susfs_guard_lkm` |

The module's own vermagic (`5.15.202-android13-5.15.202_r00-dirty`) differs from the running kernel (`5.15.149-android13-8-…`), and it still loads: `ksud insmod` loads with kallsyms access and skips the module version check, and the guard matches symbols by name rather than by CRC.

### Boot persistence

A bare `insmod` does not survive a reboot, so the module ships as a KernelSU module (`susfs_guard_lkm-module.zip`, `55740001f1133f067b324a316c779fe8907275d120dfc94cb9d8cef359ac9f66`): `module.prop` plus `post-fs-data.sh` and `service.sh`, both of which call `/data/adb/ksud insmod /data/adb/modules/susfs_guard_lkm/susfs_guard_lkm.ko` and return early when `/sys/module/susfs_guard_lkm` already exists.

After `adb reboot`, `/data/adb/ksu/log/susfs_guard.log` records `2026-11-02 17:18:27 loading …` and `17:18:29 rc=0 present=yes`; root kept working, SELinux stayed Enforcing, and `init_boot` was not touched again.

`ksud susfs module install` is a different thing: it writes `susfs_manager` (v4.0.0), a settings module that re-applies saved SUSFS configuration at boot. It neither ships nor loads an LKM.

## Known gaps

- **Kernel path (`boot-<variant>.img`) is untested on hardware.** The chain descriptor for `boot` in `vbmeta_a` points at key `d46eb3be…`, which is Meizu's, so the expectation is rejection; that expectation has not been measured.
- **`vendor_boot` is enforced**, so OrangeFox/SHRP/Lineage Recovery in `vendor_boot` do not load. Recovery work on this phone has to go through `init_boot` (the LKM path) instead.
- **SUSFS does not hide the manager app and does not pass Play Integrity.** Apps that call the Integrity API need a separate PIF-style module.
- **ROOT via LKM only.** Nothing here proves a rebuilt kernel boots, even though the ABI gate shows zero CRC mismatches.
